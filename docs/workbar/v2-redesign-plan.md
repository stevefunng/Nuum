# NunuBar V2 重构计划：顺序日志、同步水位与简单接力

> 2026-10-15 · 已审阅并实施；验证范围见 [implementation.md](./implementation.md)。
> 替代旧统一 RoomState / reducer 方案。foundation.md 与 implementation.md 已统一到当前实现。以下保留审阅时的设计理由和验收要求。
> 范围：本地 Room / NunuBar。跨用户功能推迟 V3，本期只固定可沿用的房间顺序契约。

## 1. 核心修正

**群聊顺序不需要调度状态机。采用单一顺序日志、客户端同步水位表、Grokbot 式顺序执行循环。**

上一版把三个问题混到了一起：房间消息的顺序与同步、session 已收到的模型输入、讨论或卡片是否执行完成。再用统一 RoomState 解决它们，扩大了复杂度。此次明确拆开：

| 问题 | 最小机制 | 明确不承担的职责 |
|---|---|---|
| 所有人看到相同的群聊顺序 | 房间权威日志的 `seq` + 客户端同步水位表 | 不决定谁醒、不证明模型读过或任务完成 |
| 主 session 不重复灌入相同群聊内容 | session 自身输入记录中的房间输入位置 | 不决定气泡顺序、不驱动接力、不在房间再写确认记录 |
| 谁接着讨论 | 一段有界异步循环 + 现有 Nunu 独占执行槽 | 不持久化轮次和成员下标、不恢复循环程序位置 |
| 卡片派工与回报 | 卡片业务事件 + 最少的执行开始／结束记录 | 不建立通用 outbox/inbox 或工作流状态机 |

删除原计划中的统一 Room reducer、持久化 discussion/workItems 状态集合、两张执行转换表、跨文件输入确认补偿链，以及后台多批追赶调度。保留已有业务投影函数；投影函数并不因此成为调度引擎。

有少量变量、业务状态和执行记录是必要的，但不再将其组合成一套需要多个模块共同推进的持久状态机。

## 3. 群聊顺序：先确定唯一顺序，再谈水位

### 3.1 直接复用 Work timeline

现有 `packages/host/src/work-store.ts:appendEvent` 已按房间串行追加，分配 `lastSeq + 1` 并同步落盘。沿用该机制，避免另建一条聊天排序链。

- 每个房间一个权威写入点。本地是 Host；未来多用户由一个房间权威服务接收各用户／agent 提交，再分配同一序列。不能让各客户端自行分配房间 seq。
- 已提交事件以 `(roomId, seq)` 排序，`eventId` 标识事件，沿用 `clientEventId` 表达请求重试身份。相同请求重试返回原事件；同一身份不同内容显式报冲突。
- 时间戳只用于展示，不排序；各 Nunu 私有 transcript 的 seq 只在各自 session 内有效，不能拿来合并群聊。
- 卡片摘要与状态变更仍是同一个房间事件，聊天与卡片投影不会各自争抢顺序。
- 回复、派工和结果保存来源事件引用；依赖的来源先提交。并发且无依赖的消息按权威接收顺序排列，不承诺还原不同设备的物理发送时间。

**seq 决定顺序；水位记录一个客户端已完整取得并应用了哪一段顺序。水位本身不能创造全局顺序。**

### 3.2 水位表的唯一含义

```text
RoomSyncWatermark
key:   roomId + replicaId
value: appliedThroughSeq
```

`replicaId` 是消费这份房间投影的客户端实例／缓存副本。未来同一用户的两台设备有各自一行，不能共用一条 user 水位；agent 模型 session 不是此表的主体。以后若有程序客户端复制房间日志，它也按副本身份消费。

`appliedThroughSeq = 42` 只表示：该副本已完整应用权威日志截至 42 的内容。它不表示用户已读、agent 已读、已经回应或卡片已完成。V2 不另外实现阅读回执。

表由消费端维护，正常接收路径必须读取、比较和更新它。没有持久缓存时就在内存保存，重新打开从完整快照建立；有持久缓存时，缓存与水位必须一起提交。禁止只持久化数字，却没有与之对应的投影内容。

### 3.3 V2 先用完整快照，V3 再接增量同步

V2 沿用现有 `workGet` 快照路径，在返回值明确增加与该快照内容一致的 `throughSeq`，客户端以水位表防止回退：

1. 收到完整快照，核对 roomId、当前订阅／请求归属。
2. 只有不旧于已应用版本的快照才能替换该房间投影，投影和水位一起更新。
3. 例如 42 的快照先返回，41 后返回，后者必须丢弃；切到另一个房间后也不能被旧请求覆盖。
4. 快照的 throughSeq 必须来自构造快照所使用的同一份日志前缀，不能投影旧内容后再读取一个较新的 head。

这里有直接的现有修复目标：`apps/desktop/src/renderer/App.tsx:loadWork` 目前 await 返回后直接 `setWorkSnapshot`，没有上述版本及房间归属检查。

V2 不为尚未存在的网络传输建设重排队列、远端 ACK 服务或同步数据库。V3 的增量接入遵守同一水位含义：

- 收到下一个连续序号才应用；旧事件去重；出现缺口先补齐，不能把水位直接设为收到过的最大序号。
- 例如当前为 40，先收到 42，先保留 42；收到 41 后再依次应用 41、42。重传 41 不重复出气泡。
- 同一 seq 对应不同事件视为数据冲突，停止应用并重新校验，不靠 eventId 字典序强行排序。
- 快照可一次建立完整前缀，之后只接更大的增量；旧快照不能覆盖已应用的新消息。

房间 seq 包含非聊天事件。例如 41 是聊天、42 是卡片更新、43 是聊天，气泡没有 42 很正常。水位针对完整事件前缀，不针对“渲染出来的气泡数量”。未来若按权限过滤事件，服务端需提供获准范围的覆盖证明或独立流版本；不能把权限不可见误判为漏包。该协议留 V3 实现。

成员目录等不在 timeline 内的数据继续使用各自已有 revision，不假装一个聊天水位能版本化所有文件。

### 3.4 流式输出与未确认发送

正式气泡只有提交后才进入 room seq 顺序。发送中／流式内容使用临时展示和稳定关联 ID；确认后去重替换为正式事件，不能按本机到达时间插入权威历史。临时内容的位置不承诺跨客户端一致，正式气泡的相对顺序不能事后改写。

不转发 agent 私有 transcript 到群聊。只有获准的公开消息或卡片摘要进入房间日志。

## 4. 唤醒与接力：规则集中，执行只用循环

| 输入 | 行为 |
|---|---|
| 用户无 @ 普通发言 | Room 与 NunuBar 一致，启动成员讨论 |
| 用户 @成员 | 按提及选择回应成员；@all / @everyone 选择全员 |
| 当前讨论中的 agent 回复 | 由当前循环继续；不另开一场讨论 |
| 当前讨论中的 agent @成员 | 下一轮重算目标时生效，不递归唤醒 |
| 卡片进度／交付／阻塞摘要 | 正常入群聊；不启动全员讨论，不刷新讨论预算 |
| 派 worker / worker 回报 | 分别唤醒 worker / 固定负责人的卡片 session |
| 报告阻塞 | 暂停卡片，等待用户确认，不自动接力 |

实现集中保留两个职责：纯策略函数决定本轮成员和上限；普通 async 函数顺序执行。不要把此表翻译成一套通用状态转换框架。

循环仅在内存保存 round、order、计数、失败成员以及停止标记。每房间最多一场讨论；每个成员运行经过现有 Nunu 执行槽，实际获得槽位后再取最新获准输入。

- 最多三轮、总共十条公开回复、每成员每次最多两条；十条不是十次模型调用。公开写入入口在提交前检查额度，不能提交后才截断 UI。
- 每轮开始按本次用户输入及后续讨论回复累计提及，按 round 轮换起始成员。普通卡片广播不参加提及选择或讨论计数。
- 整轮无人公开发言就结束；pass 不公开。错误必须可见，失败成员本场不自动重试，其余成员可继续。
- 成员候选集在讨论开始时确定，加入者下场参与；退出者后续跳过，公开提交时再检查资格。
- 新用户消息到来：尚未开始的旧步骤失效；已经开始的成员可以完成并公开回复，然后停止旧接力。期间多条用户输入合并启动下一场，保留全部正文和提及。该批输入是对 Grokbot“最近一条用户消息”的明确扩展，避免连续补充丢失。
- 用户明确停止：取消后续步骤、请求停止当前执行；通过当前 run 的取消标记拒绝迟到公开写入。新用户补充与明确停止不能共用这个拒绝条件。

重启后不恢复“第二轮第三位”。中断讨论显示已发表内容与中断提示，用户继续时启动新一场有界讨论、沿用原主 session。未开始的用户输入可以重新合并排队；已经开始但是否执行完不确定的输入不自动重跑。

## 5. 模型 context：原审阅记录（已被后续方案替代）

> 本节的永久输入位置与 compact 后沿用规则已撤销。当前采用“连续同群增量、重新进入补最近 24 条”，以 foundation.md 和 compact-pipeline.md 为准；以下仅保留变更缘由。

私聊和普通本地群聊仍用 Nunu 主 session；卡片按参与 Nunu 使用独立 session。同步水位不随模型 compact/reset 改变。

为避免重复投喂，沿用 session JSONL 的结构化 room input 记录：包含 roomId、输入范围、来源消息 ID、session 代际与稳定 inputId。它与实际 user prompt 同条持久记录，唯一证明该 session 已接收什么。

- session 加载时建立轻量输入位置索引，追加输入后更新内存索引；不每轮扫描完整 transcript，也不再向 room 写第二份 received 确认。
- 持有 Nunu 槽时固定输入上界，按 seq 构造新增内容。写入成功后才更新索引；沉默不导致重复注入。
- 重启从 session 记录重建输入位置；输入已落盘而模型未结束，仍属于执行不确定，不能凭输入位置自动重跑。
- compact 检查点保留输入位置元数据；reset 创建新的输入代际。它们都不能改变房间顺序或客户端同步水位。
- 主 session 已有明确公开消息凭据时可省略自己的重复正文；自己卡片 session 发出的摘要仍需进入主 session，不能按作者相同跳过。

不再把“每次必须 24 条”当作同步规则。常规仅加入新增内容；24 是 Grokbot 的历史窗口取舍，不是顺序正确性的条件。这里建议取消硬性 24 条批次，按模型输入预算限制新增内容，减少另设追赶循环的需求。

积压超出可表示范围时，先使用现有 context/compact 能力处理已在 session 内的历史；若仍装不下新增内容，明确显示上下文不足，保持输入位置不变。用户可缩小本次历史范围并明确重新建立输入起点；未读旧消息仍保留在房间，可按需读取。不能悄悄取最后 24 条后宣称此前全部已接收。本次不建设后台摘要服务或自动追赶调度；代价是极大积压可能需要用户处理。

## 6. 卡片与执行安全：保留必要业务记录

卡片创建 Nunu 固定负责；一张卡片最多一个未结清 worker 委派；worker 完成回到负责人卡片 session，负责人交付后等待人工验收。blocked 只有用户确认才能解除。卡片现有业务状态及合法转换校验保留，这是产品本身的状态，不是新增群聊状态机。

持久工作来源就是派工／回报业务事件。执行身份由来源事件和目标确定，不再为同一事实额外写 dispatch.requested、outbox、inbox 三套记录。

只为需要恢复判断的工作保留最少执行证据：来源、目标 session、runId、开始记录、结束结果。开始记录必须在调用模型／工具前落盘；已开始而没有确定结论，启动恢复时显示中断。讨论也只需知道哪批用户输入是否开始／结束，不存每轮 order/index。

恢复时做一次来源与执行记录核对：没有开始过且仍有效的工作可排队；已确认结束的不再执行；开始过但结论不确定的等待用户继续。用户停止、取消或源事件已被新输入接替的工作不得被恢复扫描重新激活，相关控制结果需有持久记录。内存队列只是现有执行槽的等待列表，不是另一套持久工作真源。

worker 提交结果时，一条事件同时完成公开摘要、卡片更新及回报关系。负责人接续以该结果事件为来源，即使提交后进程退出，也能识别尚未开始的接续。重复请求返回原结果；过期委派的迟到结果不能覆盖新的卡片版本。继续之前核对已提交结果，不承诺外部工具 exactly-once。

同 Nunu 的私聊、群聊、卡片共用一个执行槽；不同 Nunu 可并行。本轮不新增抢占、公平权重或优先级状态体系。等待 worker 时负责人结束当前 run 并释放槽；正在执行工具或等审批的 run 不伪装成已安全结束。

session 隔离不等于文件系统隔离。卡片工具沿用 session 绑定的 shell/workspace；共享可写目录必须串行使用或隔离，不能因为 Nunu 不同就允许冲突写入。未知后台进程不自动重新执行。

## 7. 实施与迁移顺序

1. **先修顺序。** 给房间快照明确 throughSeq，接入真正被读取的客户端水位表，修复旧快照回退和跨房间请求覆盖。沿用现有日志 seq，不建设 V3 网络同步。
2. **替换接力。** 唤醒规则与限额集中定义，采用 Grokbot 顺序循环，移除 runtime 中递归补派和历史猜测；Room / NunuBar 无 @ 行为一致。
3. **拆开输入。** session 输入记录成为唯一输入位置依据，加载时建索引；删除独立 cursor 文件写入及跨文件确认补偿。
4. **收拢卡片恢复。** 业务事件直接作为工作来源，最少执行记录用于恢复；验证 worker → owner → 人工验收和阻塞确认。
5. **迁移后清理。** 备份数据，保留旧公开日志与 card session；旧不确定任务需确认。新旧调度不能同时运行。验收后统一 foundation / implementation / AGENTS 并删除失效实现。

特别注意：旧 `cursors.json` 代表模型输入位置，**不能迁成客户端同步水位**。同步水位只能由已应用的完整房间快照／事件前缀建立；旧 session 输入凭据只用于恢复输入索引。

日志的完整坏行必须报错，不能静默吞掉后继续分配 seq；撕裂尾行按明确修复规则处理。若不能确定有效提交边界，停止该房间写入并提示恢复。保持已有追加、幂等与版本冲突能力，不借简化取消这些边界。

## 8. 验收重点

- 相同无 @ 输入在 Room、NunuBar 都能唤醒；提及、轮换、三轮／十条／两条、沉默停止符合规则。
- 连续用户补充不丢消息、不抹掉已开始的有效回复；明确停止后不再公开迟到结果。
- 42 快照先于 41 返回、跨房间切换、重复提交、卡片非聊天 seq，均不造成气泡回退、重复或错房间。V3 增量契约另验证乱序补缺，不宣称本期已实现远端同步。
- A/B 连续对话和沉默成员不重复注入已接收内容；输入索引重建、compact/reset 不影响群聊同步表。
- 同一 Nunu 多来源单槽；卡片 worker 回报只产生一次负责人接续；阻塞必须用户确认。
- 在输入追加、执行开始、公开结果提交、结束记录等边界中断，已提交结果不重复，不确定工具不自动重放；取消的工作不复活。
- 实施时完成类型检查、依赖检查、对应行为测试及真实 Electron 路径验证；实际验证结果以 implementation.md 为准。

**V2 不实现：跨用户网络、分布式多主排序、远端 ACK 服务、持久化群聊程序位置、通用工作流引擎、同卡多 worker 汇合、工具抢占或未知副作用自动恢复。**
